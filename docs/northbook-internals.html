Northbook · How it all works

The whole flow, simply

One agent, three front doors, four kinds of memory, two clouds-worth of plumbing — explained the way you'd explain it to a new teammate.

1 · The idea in one paragraph

Northbook is a pre-sales assistant that never forgets a client. Documents (proposals, SLAs, memos) live in a filing cabinet; facts from past meetings ("their CTO is Ruwan", "budgets approve in November") live in a notebook shared by the whole account team. When you ask something, an AI model (Gemini) decides which drawer or page to consult, tools fetch the real content, and the answer always cites where it came from. Everything is locked to one client at a time — chosen by the application, never by the model or the user's typing.

2 · The map: what talks to what

There are three ways in, one brain in the middle, and two places things are stored. Green parts run on your machine; blue parts are Google Cloud.

The one safety fact to remember: Gemini has no hands. It proposes tool calls; Python code executes them. Every read and write goes through a tool that checks the client scope first.

3 · One message, start to finish

Say Kasun opens Northbook, picks LankaPay, and types "Brief me on this client before my call." Here is everything that happens:

  1. The app sets the scope — before any AI runs. The Northbook backend creates a session with user_id = client_lanka_pay and puts client_id + person into session state. Kasun never typed the client id; picking it in the sidebar told the server, and the server told the session. (No client set? A guard callback refuses the whole turn.)
  2. The Runner assembles the request. It takes the agent's instruction (with the client id injected into the prompt text), the conversation so far, and a menu of the five tools — just their names, parameters and docstrings, never their code — and sends it all to Gemini.
  3. Gemini reads the question and picks from the menu. The instruction says "before briefing anyone, check the account memory" — so it answers not with text but with a request: recall_client_memory("decision makers, constraints, deadlines").
  4. The tool runs — in Python, on your machine. It reads client_id from state and asks Memory Bank: what do we know about this client? Back come extracted facts: "Nadeesha Silva heads switching operations… furious about the HSM incident… wants a quarterly drill discussed in November."
  5. The result goes back to Gemini, and the loop repeats. Now it wants documents: list_client_artifacts() returns compact references (name + one-line summary — never the contents), then fetch_artifact("incident_credit_memo.txt@v0") pulls one full document from the filing cabinet on disk.
  6. Gemini writes the briefing — stakeholder mood from the notebook, incident figures quoted from the document, each with its source named — and the Runner streams it back to the browser. Every step (tool call, result, final text) was recorded as an event in the session, which is exactly what the Run inspector drawer shows you.

4 · The four kinds of remembering

The easiest way to keep the whole design in your head:

TierPlain wordsLivesExample here
Conversationwhat was said in this meetingAgent Engine session cloudthe chat you're looking at
Statewhat is known right now, by keyon the sessionclient_id, person
Artifactswhat was produced — whole documentsfiling cabinet disksla_addendum.txt@v1
Memorywhat was learned across meetingsMemory Bank cloud"CTO is Ruwan; budgets in November"

Two details that make this work at scale: documents never sit in the conversation — the model sees a reference like sla_addendum.txt@v1 · 830 bytes and fetches the body only when a question needs it (so a 200-page file costs nothing until opened); and saving a document with the same name again makes a new version, with the old ones kept.

6 · The locks: one client at a time

Three rules, enforced in code (not in the prompt), keep clients sealed off from each other:

Rule 1 — the scope is set by the caller. chat.py takes the client id as a command-line argument; Northbook takes it from the sidebar click. Either way it lands in session state before the model runs. Malformed or missing → "Session refused", and the model is never even called.

Rule 2 — every tool checks it. All five tools read state["client_id"] themselves and address storage with it. The model cannot pass a different client as an argument, because no tool accepts one.

Rule 3 — storage is partitioned by that id. Artifacts live under …/users/<client_id>/… on disk; memories are filed under the client in Memory Bank. Asking Golden Lotus's session "any SLA credits pending?" finds nothing of LankaPay's — verified automatically by run_step5_isolation.py, which fails the build on any leak.

7 · The plumbing gotcha worth knowing

Sign-in is Application Default Credentials (gcloud application-default login) — no API keys in the code. One quirk of our project: Gemini models are served only on the global endpoint, while the Agent Engine (sessions + Memory Bank) lives in us-central1. So every launcher sets two locations — GOOGLE_CLOUD_LOCATION=global for the model, AGENT_ENGINE_LOCATION=us-central1 for storage. If briefing suddenly fails with "model not found" or "ReasoningEngine does not exist", one of those two is set wrong. That's the whole debugging guide.

8 · Which file does what

agent.py

The agent: instruction, tool list, and the no-client refusal guard.

tools.py · artifact_store.py

Filing cabinet: upload / fetch / list, client-scoped, versioned, on disk.

memory_tools.py

Notebook: recall_client_memory and memorize_meeting, both explicitly client-scoped.

services.py · memory_config.py

Chooses real Vertex services when configured, in-memory stand-ins otherwise. Same agent either way.

crm_app.py · webapp/

Northbook: the backend that owns client scoping, plus the console UI with the Run inspector.

chat.py · run_step*.py

Terminal chat, and the scripted proofs: memory across people, isolation, refusal.

web_app.sh · run_vertex.sh · web_observe.sh

Launchers that set the auth + two-location environment so you never have to.

test_flows/TEST_FLOWS.md

Ready-made scripts per client, with expected answers to verify against.
